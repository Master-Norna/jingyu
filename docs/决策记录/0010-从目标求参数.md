# ADR-0010 从目标求参数：求机位与求光

- 状态：已采纳（2026-09-26）

## 背景

第三次实测里最费轮次的不是“看不出哪里不对”，而是“知道要什么却调不到”：模型想让静物
落在画面左三分之一、占三分之一高，只能改相机坐标、渲染、看，再改；`look_at` 的偏移是
用“画面宽 = 传感器宽 / 焦距 × 距离”手算的。想让清晨的阳光透过窗落在桌面某一点，先用
tan(高度角) 估，没算准，最后靠 light 视图一轮轮试出来。这些都是可以反过来算的问题：
目标明确，场景完整，渲染器的几何主机侧也有。

## 决定

- 主机侧建立与渲染一致的几何：灯和相机的朝向改在纯核心里计算（worker 直接使用），
  `camera.py` 按 Blender 的镜头模型投影和反打视线，`geometry/raycast.py` 用包围盒层次树
  回答任意方向的射线。集成测试逐项比对主机投影和 Blender 渲染。
- 新增两个求解工具，都不渲染，返回可直接交给 `edit_scene` 的操作和改好的场景：
  - `frame_subject`：给出主体（物体或编组）、它在画面中的位置和占比，求相机。默认保持
    相机看主体的方向和焦距、求距离；也可以固定距离求焦距，或给出方位角和仰角。
  - `aim_sun`：给出阳光要落到的地方（世界点、物体、画面上的一点）和要穿过的洞口，求
    太阳高度和方位；可以固定其中一个角求另一个。每个候选方向都用射线检查有没有被挡住。
- 求解结果附带预测：主体和其他物体在画面里的位置；阳光穿过洞口后落在哪些物体上、落在
  画面哪一块；以及警告（相机在墙里、主体被挡、目标背光、太阳太低）。
- 求解给的是起点，不是验收：看图仍然是判断画面好坏的唯一依据（ADR-0006）。

## 后果

- 构图和布光的“调参回合”变成一次求解加一次渲染确认；实测中预测与渲染的误差在 1 像素
  左右。
- 求光把“照亮一件物体”理解为照亮相机看得到的那部分，所以逆光时会如实报告只有少部分
  受光，而不是只照亮一个点。
- 洞口（`Portal`）成为几何输出的一部分：墙的门窗洞带着生成它的参数路径，定位也用它说明
  背景像素是透过哪个洞口看到的。
- 求解只考虑直射的几何，不估计亮度；曝光和明暗仍以渲染为准。
