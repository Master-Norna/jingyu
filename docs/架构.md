# 架构

景语把“画一张图”拆成一条可追溯的链：**场景描述 → 校验 → 隔离渲染 → 不可变候选 →
看图与定位 → 改场景 → 再渲染**。每一环都有稳定的数据格式和错误码，模型、CLI 和人
走的是同一套工具。

## 分层

```
┌─────────────────────────────────────────────────────────────────────┐
│ 接入层      cli.py            mcp_server.py / mcp_entry.py          │
├─────────────────────────────────────────────────────────────────────┤
│ 工具层      tools/registry.py（输入输出 JSON Schema 校验）            │
│             tools/builtin.py（13 个工具）                            │
├──────────────┬──────────────┬───────────────┬───────────────────────┤
│ 场景描述     │ 渲染与候选   │ 看图与定位    │ 宪法与诊断            │
│ scene/       │ render.py    │ views.py      │ constitution.py       │
│              │ candidate.py │ locate.py     │ doctor.py             │
│              │ workspace.py │               │                       │
├──────────────┴──────┬───────┴───────────────┴───────────────────────┤
│ 进程边界            │ bridge/（发现运行时、启动 worker、超时与崩溃）  │
│                     │ blender/（在 Blender 内运行：kit、build、passes）│
├─────────────────────┴───────────────────────────────────────────────┤
│ 纯核心（仅标准库，主机与 Blender 两侧共用）                          │
│ errors  canonical_json  conventions  generator  idmask              │
│ geometry/（几何算子）   materials/（材质族）                         │
└─────────────────────────────────────────────────────────────────────┘
```

依赖只能自上而下。`tests/test_import_boundaries.py` 用静态分析守住三条边界：

1. **纯核心只依赖标准库**。它要在 Blender 自带的 Python 里运行，不能假设那里装了
   jsonschema、Pillow 或 mcp。
2. **`blender/` 只依赖纯核心和 bpy**。它不做校验：进入 worker 的场景已经在主机侧
   校验并补全了默认值。
3. **只有 `mcp_server.py` 导入 mcp**。MCP 是可选依赖，缺失时 `jingyu-mcp` 给出安装
   提示而不是抛出导入错误。

## 生成器：几何与材质的统一抽象

几何算子和材质族都是 `GeneratorDef`（`jingyu/generator.py`）：名字、一句话摘要、
参数表（JSON Schema 片段）、纯函数 `run`、可选的跨参数检查 `check` 和示例。

- **参数表是唯一来源**。场景 Schema、默认值补全、`list_generators` 的目录和
  [生成器目录](生成器目录.md) 都由它推出，不存在第二份手写说明。
- **必填当且仅当没有默认值**，每个参数都必须写描述；注册时强制。
- **`run` 是纯函数**：几何算子返回 `MeshData`（顶点、面、平滑、锐边），材质族返回
  `Recipe`（线性色彩空间的 Principled 通道）。它们不碰 bpy，所以能在主机上直接测试：
  每个几何算子的输出都必须是闭合流形、外法线、体积为正。
- **跨参数约束在 `check` 里**（比如器皿的 `belly_at < neck_at`），语义校验会把问题
  定位成 `spec.invalid_parameter` 加 JSON Pointer。

旋转体是第一批几何的公共底座：任何轴对称的形状都化约为把一条 (r, z) 折线从轴到轴
逆时针旋转一周（`geometry/lathe.py`）；有壁厚的器皿再向内偏移出内壁，口沿是平的。
`vessel` 就是在这之上用 PCHIP 曲线把底、腹、颈、口四个半径串起来。

新增一个算子或材质族，只需要写一个 `GeneratorDef` 并在包的 `__init__.py` 注册；
Schema、文档和工具目录会自动跟上（`python -m jingyu.reference --write`）。

## 场景描述

`jingyu.scene.v1` 是唯一事实来源，格式见 [场景描述](场景描述.md)。校验分三步
（`scene/validate.py`）：

1. **严格解析**：重复键、NaN、Infinity 直接拒绝（`json.*`）。
2. **Schema 校验**：由生成器注册表组装的 Draft 2020-12 Schema。判别联合用
   `if`/`then` 而不是 `oneOf`，这样错误能落到具体字段上。
   正则按 JSON Schema 规定的 ECMA-262 语义匹配（`$` 只匹配字符串结尾，
   `jingyu/schema_validation.py`），所以 `"vase\n"` 这样的 id 不会混过去。
3. **语义校验**：id 唯一、引用存在、生成器的跨参数检查、相机或灯看向自身、裁剪范围、
   空场景与无光的警告。

校验通过后得到补全默认值的规范化场景和它的内容哈希（规范 JSON 的 SHA-256）。之后
所有环节只接触规范化场景。

## 进程边界：为什么 Blender 在子进程里

- **隔离崩溃**：Blender 崩溃、卡死或泄漏内存不影响 MCP 服务器。
- **可换运行时**：同一协议既能驱动完整的 Blender 可执行文件，也能驱动 pip 安装的
  `bpy` 模块。`bridge/discover.py` 的查找顺序是 `JINGYU_BLENDER`、
  `JINGYU_BPY_PYTHON`、PATH 上的 `blender`、当前解释器里的 bpy、常见安装位置。
- **协议有版本**：主机写 `request.json`（`jingyu.worker.v1`），worker 原子写
  `response.json`。主机只信任响应文件：没有响应就是 `blender.crashed`，超时整组进程
  杀掉并报 `blender.timeout`，响应格式不对报 `blender.bad_response`。Blender 的
  全部输出进 `blender.log`，随候选保存。

worker 内部（`blender/`）：

- `compat.py` 收拢所有版本差异（EEVEE 在 4.2–4.5 叫 `BLENDER_EEVEE_NEXT`、5.0 起叫
  `BLENDER_EEVEE`；Principled 输入名；视图变换名；GPU 后端），最低支持 Blender 4.2。
- `kit.py` 是 bpy 的二次封装：只走 `bpy.data`，不走依赖上下文的 `bpy.ops`；统一米、
  Z 向上、物体原点在底面中心；材质以 `Recipe` 一次写入 Principled BSDF。
- `build.py` 把规范化场景搭成 Blender 场景并配置渲染；`passes.py` 渲染 ID 遮罩。

## 候选：每次渲染都是新的、不可变的

渲染先写进 `candidates/.staging/<uuid>/`，检查齐全后生成回执，再用 `os.replace`
一次性发布成 `candidates/<candidate_id>/`。候选目录包含：

| 文件 | 内容 |
|---|---|
| `scene.json` | 渲染时的规范化场景 |
| `image.png` | 图像 |
| `id_mask.png` | 精确 ID 遮罩：每个像素的 RGB 编码一个物体序号，背景透明 |
| `id_map.json` | 序号 → 物体 id、JSON Pointer、材质（`jingyu.id-map.v1`） |
| `blender.log` | worker 的完整输出 |
| `receipt.json` | 回执（`jingyu.receipt.v1`）：场景哈希、质量档、渲染参数、Blender 版本与设备、耗时、警告，以及上面每个文件的 SHA-256 |

`candidate_id` 形如 `c_20260926T040449Z_00ba7587_336e`：时间、场景哈希前 8 位、随机
后缀。`get_candidate` 每次都重算文件哈希，被改动过的候选报
`candidate.integrity_mismatch`。

ID 遮罩单独用 Cycles 渲一遍：1 采样、像素滤波宽度 0.01、Raw 视图变换、不抖动、
透明背景，所有物体换成把物体颜色直接发光的材质。这样每个像素都精确属于一个物体，
不存在抗锯齿混色。

## 看图与定位

“模型知道不对劲却说不出哪里不对”是这一层要解决的事：

- `view_candidate` 提供几种看法：`glance`（缩到拇指大）、`squint`（眯眼，模糊）、
  `grayscale` 与 `values`（明暗分级）、`flip`（镜像，打破熟视无睹）、`id_mask`、
  `compare`（和另一个候选并排）。
- `locate_in_candidate` 把一个点（像素或归一化坐标，可带半径）或一个框翻译回场景：
  物体 id、材质 id 和它们在场景里的 JSON Pointer。模型只需要指出位置。
- `describe_layout` 给出每个物体的面积占比、包围盒、重心、是否贴边，以及背景占比和
  出画的物体。
- `render_scene` 的 `hide` 参数做减法审查：去掉一个物体再渲染，对比它是否在为画面
  出力。

## 工具层

`tools/registry.py` 与传输无关：每个工具声明输入输出 JSON Schema，调用时双向校验，
失败统一成 `{"error": {...}}`。`cli.py` 和 `mcp_server.py` 都只是适配器，所以两者
的行为一致。工具清单见 [工具](工具.md)。
