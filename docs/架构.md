# 架构

景语把“画一张图”拆成一条可追溯的链：**场景描述 → 校验 → 隔离渲染 → 不可变候选 →
看图与定位 → 改场景 → 再渲染**。每一环都有稳定的数据格式和错误码，模型、CLI 和人
走的是同一套工具。

## 分层

```
┌─────────────────────────────────────────────────────────────────────┐
│ 接入层      cli.py            mcp_server.py / mcp_entry.py          │
├─────────────────────────────────────────────────────────────────────┤
│ 工具层      tools/registry.py（输入输出 JSON Schema 校验）            │
│             tools/builtin.py（15 个工具）                            │
├──────────────┬──────────────┬───────────────┬───────────────────────┤
│ 场景描述     │ 渲染与候选   │ 看图与定位    │ 宪法与诊断            │
│ scene/       │ render.py    │ views.py      │ constitution.py       │
│ （校验、物理 │ candidate.py │ locate.py     │ doctor.py             │
│  补丁、差异）│ workspace.py │ frame.py      │                       │
├──────────────┴──────┬───────┴───────────────┴───────────────────────┤
│ 进程边界            │ bridge/（发现运行时、启动 worker、超时与崩溃）  │
│                     │ blender/（在 Blender 内运行：kit、build、passes）│
├─────────────────────┴───────────────────────────────────────────────┤
│ 纯核心（仅标准库，主机与 Blender 两侧共用）                          │
│ errors  canonical_json  conventions  generator  idmask  placement   │
│ geometry/（几何算子、变换、空间查询）  materials/（材质族）          │
│ environments/（环境族）                                             │
└─────────────────────────────────────────────────────────────────────┘
```

依赖只能自上而下。`tests/test_import_boundaries.py` 用静态分析守住三条边界：

1. **纯核心只依赖标准库**。它要在 Blender 自带的 Python 里运行，不能假设那里装了
   jsonschema、Pillow 或 mcp。
2. **`blender/` 只依赖纯核心和 bpy**。它不做校验：进入 worker 的场景已经在主机侧
   校验并补全了默认值。
3. **只有 `mcp_server.py` 导入 mcp**。MCP 是可选依赖，缺失时 `jingyu-mcp` 给出安装
   提示而不是抛出导入错误。

## 生成器：几何、材质与环境的统一抽象

几何算子、材质族和环境族都是 `GeneratorDef`（`jingyu/generator.py`）：名字、一句话摘要、
参数表（JSON Schema 片段）、纯函数 `run`、可选的跨参数检查 `check` 和示例。

- **参数表是唯一来源**。场景 Schema、默认值补全、`list_generators` 的目录和
  [生成器目录](生成器目录.md) 都由它推出，不存在第二份手写说明。
- **必填当且仅当没有默认值**，每个参数都必须写描述；注册时强制。
- **`run` 是纯函数**：几何算子返回 `MeshData`（顶点、面、平滑、锐边），材质族返回
  `Recipe`（线性色彩空间的 Principled 通道），环境族返回 `EnvironmentRecipe`（天空、
  太阳、地平线上下的背景光）。它们不碰 bpy，所以能在主机上直接测试：
  每个几何算子的输出都必须是闭合流形、外法线、体积为正。
- **跨参数约束在 `check` 里**（比如器皿的 `belly_at < neck_at`），语义校验会把问题
  定位成 `spec.invalid_parameter` 加 JSON Pointer。

旋转体是第一批几何的公共底座：任何轴对称的形状都化约为把一条 (r, z) 折线从轴到轴
逆时针旋转一周（`geometry/lathe.py`）；有壁厚的器皿再向内偏移出内壁，口沿是平的。
`vessel` 就是在这之上用曲率连续的单调曲线（五次 Hermite，斜率取 PCHIP）把底、腹、颈、口四个半径串起来，不越过控制半径，光滑釉面上的高光也不会在控制点处折断。

新增一个算子、材质族或环境族，只需要写一个 `GeneratorDef` 并在包的 `__init__.py`
注册；Schema、文档和工具目录会自动跟上（`python -m jingyu.reference --write`）。

环境族把“场景外面的光”也做成生成器（[ADR-0007](决策记录/0007-光照环境是生成器.md)）。
`daylight` 只暴露人会用来描述天气和时间的量（太阳高度、方位、云量、雾霾、地面颜色），
在内部推出必须彼此一致的量：阳光色温随高度变化，云量同时削弱阳光、放大阴影软度、把天空
换成均匀的阴天光，地面按照照到它的光来反射。天空用 Blender 的物理散射模型（5.0 起叫
multiple scattering，4.x 叫 Nishita，差异收在 `compat.configure_sky`），关掉太阳圆盘，
再配一盏方向和颜色一致的太阳灯；天空亮度按实测标定到与太阳灯同一量级。

## 放置：关系优先于坐标

`jingyu/placement.py`（纯核心）把规范化场景解析成每个节点的世界矩阵
（[ADR-0008](决策记录/0008-放置关系与物理检查.md)）：

- 编组是不可见的变换，节点的矩阵是 `父级世界矩阵 @ T @ R @ S`
  （`geometry/transform.py`，与 Blender 的约定逐位一致）。
- `rest_on`：先把物体和支撑物变换到世界空间，再用竖直方向的射线查询
  （`geometry/spatial.py`，三角形按二维网格分桶）求出“从高处落下时第一次接触”的位移；
  这个世界竖直位移再解回物体的局部坐标，所以倾斜的编组里也成立。支撑按依赖顺序求解，
  成环或下方没有支撑都是错误。
- 主机和 worker 调用同一份代码：主机用它报错和做物理检查，worker 用它搭场景，两边的
  结果完全一致。worker 直接写 `matrix_world`，Blender 里没有父子关系。

物理检查（`scene/physics.py`）用同一份世界网格：一个物体的顶点在另一个闭合网格内部超过
1 毫米报 `physics.intersection`（内外用竖直射线的交点奇偶判断，深度取三个轴向上到表面的
最近距离）；物体离正下方的东西超过 2 毫米、又没有陷进别的东西，报 `physics.floating`。
它们是警告：钉子可以钉进墙，吊灯可以悬空。

## 场景描述

`jingyu.scene.v1` 是唯一事实来源，格式见 [场景描述](场景描述.md)。校验分三步
（`scene/validate.py`）：

1. **严格解析**：重复键、NaN、Infinity 直接拒绝（`json.*`）。
2. **Schema 校验**：由生成器注册表组装的 Draft 2020-12 Schema。判别联合用
   `if`/`then` 而不是 `oneOf`，这样错误能落到具体字段上。
   正则按 JSON Schema 规定的 ECMA-262 语义匹配（`$` 只匹配字符串结尾，
   `jingyu/schema_validation.py`），所以 `"vase\n"` 这样的 id 不会混过去。
3. **语义校验**：id 唯一、引用存在、编组不成环、生成器的跨参数检查、相机或灯看向
   自身、裁剪范围、空场景与无光的警告。
4. **放置与物理**：解析编组和 `rest_on`，再做穿插与悬空检查（见下文“放置”）。

校验通过后得到补全默认值的规范化场景和它的内容哈希（规范 JSON 的 SHA-256）。之后
所有环节只接触规范化场景。

## 进程边界：为什么 Blender 在子进程里

- **隔离崩溃**：Blender 崩溃、卡死或泄漏内存不影响 MCP 服务器。
- **可换运行时**：同一协议既能驱动完整的 Blender 可执行文件，也能驱动 pip 安装的
  `bpy` 模块。`bridge/discover.py` 的查找顺序是 `JINGYU_BLENDER`、
  `JINGYU_BPY_PYTHON`、PATH 上的 `blender`、当前解释器里的 bpy、常见安装位置。
- **协议有版本**：主机写 `request.json`（`jingyu.worker.v1`），worker 原子写
  `response.json`。主机只信任响应文件：没有响应就是 `blender.crashed`，超时整组进程
  杀掉并报 `blender.timeout`，响应格式不对报 `blender.bad_response`。Blender 的
  全部输出进 `blender.log`，随候选保存。

worker 内部（`blender/`）：

- `compat.py` 收拢所有版本差异（EEVEE 在 4.2–4.5 叫 `BLENDER_EEVEE_NEXT`、5.0 起叫
  `BLENDER_EEVEE`；Principled 输入名；视图变换名；GPU 后端），最低支持 Blender 4.2。
- `kit.py` 是 bpy 的二次封装：只走 `bpy.data`，不走依赖上下文的 `bpy.ops`；统一米、
  Z 向上、物体原点在底面中心；材质以 `Recipe` 一次写入 Principled BSDF。
- `build.py` 把规范化场景搭成 Blender 场景并配置渲染；`passes.py` 渲染 ID 遮罩。

## 候选：每次渲染都是新的、不可变的

渲染先写进 `candidates/.staging/<uuid>/`，检查齐全后生成回执，再用 `os.replace`
一次性发布成 `candidates/<candidate_id>/`。候选目录包含：

| 文件 | 内容 |
|---|---|
| `scene.json` | 渲染时的规范化场景 |
| `image.png` | 图像 |
| `id_mask.png` | 精确 ID 遮罩：每个像素的 RGB 编码一个物体序号，背景透明 |
| `id_map.json` | 序号 → 物体 id、JSON Pointer、材质（`jingyu.id-map.v1`） |
| `light_mask.png` | 光照通道：每个采样点被哪些灯直接照到（24 位掩码），没有表面处透明 |
| `light_map.json` | 灯的列表、每个物体被各灯照到和背光的比例、主要投影、在取景范围内的物体、相机周围的开敞度（`jingyu.light-map.v1`） |
| `blender.log` | worker 的完整输出 |
| `receipt.json` | 回执（`jingyu.receipt.v1`）：场景哈希、质量档、渲染参数、Blender 版本与设备、耗时、警告，以及上面每个文件的 SHA-256 |

`candidate_id` 形如 `c_20260926T040449Z_00ba7587_336e`：时间、场景哈希前 8 位、随机
后缀。`get_candidate` 每次都重算文件哈希，被改动过的候选报
`candidate.integrity_mismatch`。

ID 遮罩单独用 Cycles 渲一遍：1 采样、像素滤波宽度 0.01、Raw 视图变换、不抖动、
透明背景，所有物体换成把物体颜色直接发光的材质。这样每个像素都精确属于一个物体，
不存在抗锯齿混色。

光照通道（`blender/diagnostics.py`）不渲染，而是用 Blender 自己的射线求交：从相机对每个
采样点（长边至多 240 个）打一条射线，再从命中点向每盏灯（环境的太阳记作
`environment.sun`）打阴影射线，穿过玻璃等透射材质。于是“果子为什么暗”有了几何答案：
背对灯、被谁挡住、还是只有天光。面光按中心点算，不测半影；天光来自四面八方，不算作灯。
同一趟还算出哪些物体在取景范围内（包围盒裁到相机前方后投影），以及从相机向四周打 256
条射线有多少直达天空，用来判断房间有没有封闭。一次大约 0.3 秒。

## 看图与定位

“模型知道不对劲却说不出哪里不对”是这一层要解决的事：

- `view_candidate` 提供几种看法：`glance`（缩到拇指大）、`squint`（眯眼，模糊）、
  `grayscale` 与 `values`（明暗分级）、`flip`（镜像，打破熟视无睹）、`id_mask`、
  `compare`（和另一个候选并排）。
- `locate_in_candidate` 把一个点（像素或归一化坐标，可带半径）或一个框翻译回场景：
  物体 id、材质 id 和它们在场景里的 JSON Pointer。模型只需要指出位置。
- `describe_layout` 给出每个物体的面积占比、包围盒、重心、是否贴边，以及背景占比和
  出画的物体；还有每个物体的渲染颜色、材质颜色和两者的偏移，以及被各灯照到的比例。
- 颜色测量（`measure.py`）：材质颜色是反射率，屏幕上的颜色还乘了光的颜色、过了视图变换，
  暖色低角度阳光下的橙子会变成桃色。定位和布局把渲染出的平均颜色（hex、色相、饱和度、
  明度）和材质颜色并排给出，偏移一眼可见。
- `describe_light` 读光照通道：每盏灯照到每个物体多少、最大的几块投影由谁投在谁身上、
  相机周围多开敞。`locate_in_candidate` 也会说出某一点被哪些灯照到。
- `view_candidate` 的 `light` 视图把某盏灯照不到的地方压暗，直接看光落在哪；
  `saturation` 视图看颜色哪里浓哪里淡；任何视图都可以用 `region` 裁出一块放大看细节。
- `render_scene` 的 `hide` 参数做减法审查：去掉一个物体再渲染，对比它是否在为画面
  出力。
- 渲染完成后 `frame.py` 检查画面，结果作为警告写进回执：可见物体一个像素都没占到
  （`frame.not_visible`），整体偏暗并给出建议曝光（`frame.underexposed`），大片死白
  （`frame.overexposed`）。有光照通道时，`frame.not_visible` 只报在取景范围内却被
  完全挡住的物体，范围外的（天花板、镜头背后的墙）不再报；有窗的墙配日光、而相机上方
  大片直通天空时报 `light.open_to_sky`：天光会从四面八方灌进来，而不只从窗户进。
- `diff_candidates` 比较两个候选：场景里按 id 对齐的字段变化，和每个物体在画面里的位置、
  面积变化，用来确认一次修改确实做到了想做的事。

## 修改场景

`edit_scene`（`scene/patch.py`）用 JSON Patch 操作加 `merge` 改场景，路径段 `@<id>` 按
id 选数组元素，所以改动不依赖数组下标，也不用重写整份场景。操作全部成功才生效，失败报
`patch.failed` 并指出第几条。场景来源可以是内联场景、工作区文件，或某个候选渲染时用的
场景（`from_candidate`）。

## 工具层

`tools/registry.py` 与传输无关：每个工具声明输入输出 JSON Schema，调用时双向校验，
失败统一成 `{"error": {...}}`。`cli.py` 和 `mcp_server.py` 都只是适配器，所以两者
的行为一致。工具清单见 [工具](工具.md)。
